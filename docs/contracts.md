# Sley Contract Map

Status: v1 contract map for the self-hosting stage-1 bootstrap surface.
Last checked: 2026-08-26.

This file names the machine-readable JSON roots that external tools may
consume. Schemas live under `docs/schemas/`, representative instances live
under `fixtures/contracts/`, and the local release gate validates both with
JSON Schema draft 2020-12.

## Validation Commands

```bash
sley-contract inventory --json
sley-contract check-fixtures fixtures/contracts --json
sley-contract validate --schema sley.conformance.manifest.v0 fixtures/corpus/manifest.json --json
sley-corpus admission-check --record fixtures/corpus_governance/record.json --exclusions fixtures/corpus_governance/exclusions.json --root fixtures/corpus_governance --json
sley-corpus audit --manifest fixtures/corpus_governance/manifest.json --root fixtures/corpus_governance --json
sley-corpus audit-log --log <audit-log.jsonl> --log-id <logical-log-id> --json
sleybench-split verify-public --split <public-split-manifest> --json
sleybench-split audit --split <public-split-manifest> --private-manifest <private-case-manifest> --private-exclusions <private-exclusion-ledger> --json
sley claim-verify --json docs/SleyClaimManifest.json
sley operational-workflow plan --controller <private-controller-path> --json
sley operational-evidence assemble --reference-replay <report> --agent-comparison <report> --controller <private-controller-path> --raw-aggregate <private-report> --raw-evidence <private-directory> --structural-aggregate <private-report> --structural-evidence <private-directory> --approval-record <private-record> --execution-provenance <private-record> --json
sley-conformance report --json
make v1
```

`sley-contract` uses `docs/schemas` from the current working directory when it
exists and otherwise falls back to the bundled source schema directory.
Explicit schema paths remain supported for pinned validation. `validate` checks
one report against the requested schema; `check-fixtures` checks every fixture
against the schema named by its top-level `schema` field.

Current counts:

- Schemas: `99`
- Contract fixtures: `187`
- Schema instances: generated by `sley-conformance report --json`

The Python and Node worker reference clients expose models generated directly
from the four stable worker schemas.
`clients/generate-worker-clients.py --check` rejects checked-in model or
protocol-constant drift. The handwritten
client code owns only ordered stdio transport and exact lifecycle request
construction; worker responses remain the authority for status, failure class,
retryability, isolation, and results.

## Stability Rules

- `docs/v1.2/CONTRACT_STABILITY.json` is the machine-readable class registry;
  unlisted schemas resolve to `experimental`.
- Stable v1 shapes are frozen. Any field or semantic change requires a new
  schema identifier; their current v0 producers do not cut over implicitly.
- Every JSON root must carry a top-level `schema` string.
- Schema drift must update the matching schema file, representative fixture,
  inventory snapshot, tests, and release docs in the same change.
- Contract fixtures must validate through JSON Schema draft 2020-12.
- Runtime, deploy, sandbox, adapter, worker, and benchmark contracts must remain deterministic
  and must not require provider calls, network access, secrets, spend, or live
  deployment. The sandbox runner is seeded replay evidence; it does not claim
  OS-level isolation. The worker enforces a fresh bounded process per invoke
  but truthfully does not claim namespace containment.
